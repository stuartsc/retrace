## Pre-change audit findings

- The installed bundle remains **0.7.6 (2609.18.1)**, with source marker `83dc626c`. The host is **macOS 26.1 (25B78)**. A native API probe reports `VNRecognizeTextRequest` default revision **3**, with supported revisions **1, 2, 3**. App configuration already selects `.accurate`, English and a minimum confidence of 0.5. This is not a fast-mode configuration mistake.
- The latest twelve video metadata rows all report **3840×2160**. `VisionOCR` reduces a complete image of that size to **1763×992** under its accurate-mode 1.75-megapixel budget, retaining about 21% of the input pixel count. Small incremental crops can retain their original detail; large crops can be reduced again. This makes resolution depend on which extraction path runs. See `Processing/OCR/VisionOCR.swift`.
- The live screenshot method keeps full resolution and enables language correction. Recorded full-frame and incremental methods disable correction. Correcting ordinary prose and preserving exact identifiers are different requirements; neither setting is universally right.
- `IncrementalSegmentWriter` writes raw BGRA pixels to the recovery WAL before HEVC encoding. `FrameProcessingQueue` prefers that exact frame-ID source while it is readable. However, writer finalization removes the WAL after encoding, without waiting for durable OCR completion. Delayed processing can therefore lose access to the original pixels. See `Storage/IncrementalSegmentWriter.swift`, `Storage/WAL/WALManager.swift` and `App/AppCoordinator.swift`.
- The finalized-video OCR fallback calls `StorageManager.readFrame`, which decodes HEVC, converts the result to **JPEG quality 0.8**, and then decodes that JPEG back to pixels for OCR. This introduces a second lossy step with no text-extraction benefit. The later OCR scale reduction still applies. See `Storage/StorageManager.swift` and `Processing/FrameProcessingQueue.swift`.
- Archive encoding already uses HEVC, interframe compression and a 30-frame keyframe interval. The persisted `videoQuality` preference reads **0.70**, rather than the 0.50 default. This preference read does not independently measure the live encoder's effective quality. Native encoder enumeration confirms hardware HEVC support and returns no AV1 encoder on this installation. A codec change cannot yet be described as a size/quality improvement.
- The generic `AccessibilityService` exists, but the saved-frame extraction path deliberately cannot invoke it. App defaults disable live Accessibility text extraction, and there are no production callers of `extractTextViaAccessibility`. Existing activity enrichment provides context such as focused window/document identity, not a durable snapshot of all visible app text. The generic helper traverses application children and values; it is not ready to become capture-time evidence without window, visibility, sensitive-field, resource and timing constraints.

These are source-path and bounded metadata findings. No private screenshot, transcript or document content was inspected. They identify mechanisms that can degrade quality, not the measured frequency or cause of every reported error.

## Native technology choices

Apple's Vision remains the native OCR foundation. The newer Swift request API improves integration and concurrency; its existence does not prove higher character accuracy than the current request. [Apple's Swift Vision overview](https://developer.apple.com/videos/play/wwdc2024/10163/)

`RecognizeDocumentsRequest`, available in the installed macOS 26 SDK, adds document hierarchy, paragraphs, lists and tables. Compare it on document/window crops for reading order and structure; Apple does not establish that it wins on arbitrary desktop text or every identifier. [Apple's document-recognition introduction](https://developer.apple.com/videos/play/wwdc2025/272/)

The WWDC26 image-understanding changes also introduce image inputs/tool calling for Foundation Models, including Vision OCR tools. These merit a later capability/availability check, not replacement of literal evidence with model-generated corrections. The session itself describes combining model interpretation with specialized Vision tools for fine text. [Apple's 2026 image-understanding update](https://developer.apple.com/videos/play/wwdc2026/237/)

Use native app/window inventory and Accessibility for directly exposed text. `NSWorkspace.runningApplications` identifies running GUI applications, not every background process or document content. Accessibility visible character ranges and string-for-range APIs can read an exposed viewport without asking OCR to guess its letters; support varies by element and application. Unsupported/canvas-rendered text still needs pixels. [App inventory](https://developer.apple.com/documentation/appkit/nsworkspace/runningapplications), [visible character ranges](https://developer.apple.com/documentation/applicationservices/kaxvisiblecharacterrangeattribute), [range text](https://developer.apple.com/documentation/applicationservices/kaxstringforrangeparameterizedattribute)

Evaluate ScreenCaptureKit for application/window capture and supported display scaling. Its `.best` resolution option specifically applies to independent window capture; switching frameworks alone cannot repair downstream shrinking or JPEG conversion. [Apple's capture-resolution documentation](https://developer.apple.com/documentation/screencapturekit/sccaptureresolutiontype/best)

## Delivery order

This quality work precedes the remaining semantic index/worker integration in the progressive-recall plan. Better retrieval cannot restore a misread amount or missing character.

1. **Freeze a representative quality baseline.** Exercise initial/full-frame, incremental, backlog, restart and historical paths on the same authored corpus and later user-identified failures. Include small light/dark text, fonts/scaling, coloured code, URLs, amounts, ambiguous characters, tables, overlapping windows and multiple displays. Compare production OCR, native crops and document recognition. Record omissions separately from substitutions and layout errors; confidence is only an input, not the acceptance oracle.
2. **Preserve pixels through durable extraction.** Add a bounded, recoverable original-image lease/spool. Archive encoding may run concurrently, but original disposal requires successful durable text publication, verified archive/frame mapping and no active reader. Explicit privacy deletion still wins. OCR failure, cancellation, restart, encoder/database failure and spool pressure need tested states, not silent fallback or unbounded disk growth. One 4K BGRA frame is approximately 31.6 MiB; lossless spool compression is a candidate, subject to measured I/O/CPU cost. Separate capture finalization from OCR-source release without weakening recovery.
3. **Remove avoidable OCR losses.** Feed exact decoded pixels directly to historical OCR instead of round-tripping through JPEG. Compare bounded native-resolution window/region crops, with overlap and verified coordinate transforms, against the current full-frame budget. Preserve complete lines, source identity, cancellation and cache invalidation. Use language correction/dictionaries only under a tested policy that protects identifiers and numeric evidence. Store original and alternative extraction revisions rather than silently rewriting earlier evidence.
4. **Collect direct text at capture time.** Model display → window → pane/document → visible text. Bracket app/window identity and content sampling around the pixel observation; refuse stale/A→B→A attachments. Read bounded visible Accessibility content, with app-specific adapters where needed, and use OCR for uncovered visual regions. Preserve source method, sampling time, ownership and coverage. Window inventory, focused state, visible content and occluded/offscreen content remain distinct facts. Never use today's AX tree to enrich an old screenshot, collect hidden whole-document values as visible text, or infer activity from a running process. Existing pause/exclusion/sensitive-field rules apply to every source.
5. **Benchmark archival compression independently.** Start with the present HEVC path and quality preference as baseline. Compare higher-quality HEVC settings and supported encoder/profile controls, plus an experimental lossless changed-tile archive with periodic reconstructible keyframes. Measure text and colour fidelity after decode, bytes per captured minute, energy, encode/decode p95, random access and recovery. Probe 4:4:4 support before relying on it for coloured text. Consider AV1 only if a separately measured backend justifies its encode cost; no native AV1 encoder was enumerated here. A quality value of 1 is not a universal lossless guarantee. [Apple's quality-property contract](https://developer.apple.com/documentation/videotoolbox/kvtcompressionpropertykey_quality)
6. **Select and trial the measured result.** Require exact critical tokens and reduced character/omission error on the reviewed corpus, no incorrect app/window attribution, bounded spool storage and no more than the existing 10% foreground p95 regression allowance. Publish coverage and content-free source/quality metrics. Test source release and cancellation using real SQLite, filesystem, native capture/AX helpers and codecs. Keep the macOS 13 fallback and existing archive reader until newer paths pass; do not recompress or reprocess the entire live library as part of initial evaluation.

The intended outcome is full-detail source capture, directly exposed text wherever reliable, OCR over the remaining sharp pixels, and a compact readable archive. **No particular compression ratio, accuracy gain or production rollout is promised before those comparisons.**

## Native OCR and archive-pixel implementation — September 20

The first source checkpoint addresses avoidable OCR losses and supplies repeatable native comparisons. It does not install a new app, retain originals beyond the existing WAL lifetime, collect new Accessibility content, or change recording/codec settings. The current installed trial remains **2609.18.1**. Root coordinates the narrow Shared protocol addition; Processing owns extraction/queue changes and Storage owns the decoded-pixel implementation.

### Implemented behavior

- Accurate saved-frame OCR keeps native pixels. Images above 1.75 MP combine native whole-image discovery with overlapping native crops, since the whole-image detector alone missed small text in the authored fixtures. Fast mode retains its existing scaling. Incremental extraction still expands changed areas across complete cached lines and retains original-frame geometry.
- Crop work is bounded: 128 inspected cells, twelve grid requests and 12 MP of grid input, plus at most four seam reads of at most 1.75 MP each. Including initial discovery, the ceiling is seventeen Vision requests per large image. Exact solid-colour crops skip Vision. Native-only discovery is retained when observation/merge budgets are exceeded; the added local reconciliation is bounded to 512 observations. These are work limits, not proof that latency targets pass.
- Crops check both ends of already detected lines and reject literal prefix/suffix shortening. Whole-display boxes can have several pixels of extra padding, so unchanged/longer text permits a bounded estimated-glyph allowance (at most 12 px); shorter compact text requires 2 px endpoint coverage. This catches a missing final digit even when an earlier glyph also changes. It is conservative: an improved but shorter reread can leave the original in place if its geometry cannot establish coverage. Split words are ordered left to right within a line. Request boundaries, row stride, image allocation and cancellation are checked. Saved OCR still disables language correction to avoid silently rewriting identifiers; the separate live screenshot helper is unchanged.
- Finalized-video processing calls `StorageProtocol.readFrameForProcessing`, validates native source/video identity, frame range, path containment and exact media dimensions/time, and rasterizes decoded pixels directly to BGRA. The former HEVC→JPEG→BGRA step is removed from OCR. Presentation JPEG APIs remain available. Exact raw WAL is still preferred while readable.
- `daily_metrics` adds `ocr_source_processing` with only `source` (`wal_bgra` or `archive_bgra`) and `outcome` (`started`, `completed`, `failed`, `cancelled`). Completion follows atomic OCR/text/search publication. The metric begins after source acquisition; it excludes decode failures and source deferrals, so is not a complete attempt denominator. Metadata contains no screen text, identifiers, app names or paths. Existing OCR/capture-to-search latency metrics remain in place.

### Original retention: required next contract

Retaining a WAL directory after encoder finalization is insufficient. The next implementation must cover these connected states before changing disposal:

1. Persist original-source identity separately from current archive identity/index. Recovery can remap database frames to a new archive; queued OCR must still locate the original record by its durable capture/frame identity.
2. Distinguish encoded output from verified database publication and durable text extraction. `processingStatus = 2` also represents exclusion/skip paths, so it alone cannot authorize original release. Persist extraction/release receipts and reconcile a lost completion callback at startup.
3. Use a retained-original namespace that older recovery code will not consume and delete as an ordinary active journal. Startup recovery must return before OCR workers start; it cannot wait for those workers to finish.
4. Make explicit deletion and retention authoritative across individual-frame and cascade paths, including records not yet mapped to a frame. A shared WAL cannot physically erase one frame without compaction or separate per-frame files. A deleted source must not be resurrected by recovery.
5. Lease active readers and fence storage-root/session changes. Release requires a verified archive mapping, durable extraction or explicit deletion disposition, and no active reader.
6. Bound disk **and** producer memory. Current capture streams can buffer without limit; waiting only in the App writer would move pressure into RAM. Storage-pressure admission must not follow the generic file-write failure path, which cancels the writer and removes its journal.

LZFSE is a candidate for temporary lossless originals, subject to representative CPU/I/O and pressure measurements. It is not yet the archive format. Direct visible Accessibility text and display/window inventory remain the following delivery slice, with capture-time ownership, visible-range and sensitive-field guards from the plan above.
